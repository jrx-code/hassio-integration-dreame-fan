# Recon, 2026-08-28

Question: how can the Dreame MF10 bladeless fan be brought into Home Assistant?

## What the device actually is

Confirmed by querying the Dreame Home cloud with the account
`account@example.com` (Bitwarden item "Dreame account"), region `eu`:

| field | value |
|---|---|
| model | `dreame.fan.u2519` |
| displayName | Dreame Bladeless Fan MF10 |
| did | `-117222980` |
| mac | `aa:bb:cc:dd:ee:ff` |
| sn | `U2519E63MEU00624F2` |
| firmware | `1.8.30_1047` |
| categoryPath | `/lifeapps/fan` |
| productId | `11984` |
| scType | `WIFI_BLE` |
| firmwareDevelopType | `COMM_MCU` |
| bindDomain | `10000.mt.eu.iot.dreame.tech:19973` |
| online | true |
| wifi | SSID `ISStation_IoT`, RSSI -64, channel 11 |

The fan is already paired to the same Dreamehome account as the vacuums, so no
new account or re-pairing is needed.

## Routes that do not work

- **No HACS integration exists.** Searching turns up `Tasshack/dreame-vacuum`
  (vacuums only) and an early-alpha integration for the DREAME P-Wind10 air
  conditioner - neither covers `dreame.fan.u2519`.
- **No MIoT spec.** `home.miot-spec.com/spec/dreame.fan.u2519` is a 404. The
  `dreame.fan.*` entries on miot-spec are the older Mijia purifying fans
  (p1905, p2018, p2058, p2138, p2262, l2146). This device is not in Mi Home, so
  the Xiaomi Miot Auto integration has nothing to bind to.
- **Cloud bridges via Google Home / Alexa** would work but give a fraction of the
  controls and add a third-party dependency for a device on the local LAN.

## The route that does work

The MF10 sits on the same Dreame Home cloud API as the Dreame vacuums, and that
API is already implemented in `dreame-vacuum`
(`custom_components/dreame_vacuum/dreame/protocol.py`, class
`DreameVacuumDreameHomeCloudProtocol`). Verified working against the fan:

- `login()` against region `eu`
- `get_devices()` - the fan is listed
- `get_device_info()` - full record including wifi state
- `get_properties("<siid>.<piid>,...")` - returns live values

`tools/probe.py` wraps that protocol standalone (no Home Assistant import) and
is what produced `docs/miot-properties.md`.

Two things are verified reads only. Writing (`set_batch_device_datas`) and the
MQTT push channel the vacuum integration uses for live state have **not** been
tested against the fan yet.

## Gotchas hit during recon

- `protocol.py` imports `miio` and `paho.mqtt` at module level, but the cloud
  REST path needs neither. `tools/probe.py` stubs both. On this laptop the local
  `pyOpenSSL` is broken (`module 'lib' has no attribute 'GEN_EMAIL'`) and
  importing paho drags it in through `dns.resolver`, so the stub is load-bearing
  rather than cosmetic.
- `get_properties("")`, `"*"` and `"all"` do not enumerate. Keys must be given
  explicitly as `siid.piid`, which is why discovery is a brute-force scan.
- The account note in Bitwarden is accurate: `account@example.com` logs in with
  the stored password. The other account, `second-account@example.com`, has a
  changed password and survives only on its `auth_key`.
